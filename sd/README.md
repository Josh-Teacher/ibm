# Space Dilemma Tournament Viewer

A static HTML site for projecting classroom tournaments. Faction 2 sits on the **left**; Faction 1 sits on the **right**. Real Python strategies run in separate browser workers using Pyodide. No Python server, paid hosting, or frontend build is required.

This package is the HTML viewer. `runner.py` is its browser strategy adapter, **not** the later standalone Python tournament program.

`Space_Dilemma_Tournament_Preview.html` is a separate single-file demo you can open directly in your browser. It embeds a completed Tournament 1 generated by the real Python runtime and supports animated playback without a server or internet. Use the main site in this folder to load student strategies and conduct live tournaments. `demo/tournament-replay.json` is the same example's reusable replay record.

## Publish on GitHub Pages

1. Extract the ZIP. Put the **contents of `tournament-viewer/`** at the root of a new GitHub repository. Keep `index.html`, `styles.css`, `runner.py`, `js/`, `vendor/`, `f1/`, `f2/`, and `demo/` together. Also include `.github/workflows/pages.yml`.
2. Put Faction 1 submissions in `f1/` and Faction 2 submissions in `f2/`. Both factions must have equally many strategies. Ordinary `.py` filenames, including spaces, are supported; capitalization must match.
3. In your repository, choose **Settings → Pages → Build and deployment → Source: GitHub Actions**.
4. Push to the `main` branch. The included workflow indexes the Python files, assembles the static site, and publishes it. It does not run student code during deployment. If your branch has another name, change `branches: [main]` in the workflow.
5. Open the published URL. The official roster loads automatically. Open **Setup** to choose rules and presentation. **Reveal & start** displays the surprise multiplier before the tournament launches.

For branch-based Pages hosting instead, run `python3 tools/build_manifest.py` first, commit the two `manifest.json` files, and choose the repository root as the published directory. The Actions route does this indexing automatically whenever you push.

To host beside an existing Strategy Lab in the same repository, keep this package in a separate `tournament-viewer/` subfolder and publish it through that repository's existing Pages setup. Run `python3 tournament-viewer/tools/build_manifest.py` before publishing, or add that step to your existing workflow. Open the resulting `/tournament-viewer/` URL. All viewer asset paths are relative and support subfolder hosting; the included workflow above is configured for the new-repository root layout.

GitHub Pages publishes the strategy files along with the site. Use your normal classroom submission process to collect code before adding it to the repository.

## Try it locally

From the `tournament-viewer` directory:

```bash
python3 tools/build_manifest.py
python3 -m http.server 8000
```

Open `http://localhost:8000` in a current desktop browser. Opening `index.html` directly from your file manager does not support the worker and file-fetch features.

If the official folders are empty, open **Setup → Load demo roster**. Demo strategies are clearly labeled and kept outside `f1/` and `f2/`. They never substitute automatically for missing student files.

To rename strategies in the interface, edit the `name` fields in the faction manifests. The indexing helper preserves existing names when regenerating the lists.

## Strategy contract

Each `.py` file must define:

```python
def space_exploration_strategy(history, round_number, resource_multiplier):
    return "K" if round_number % 3 == 0 else "S"
```

- Return exactly `"S"` for Share or `"K"` for Keep. The words `"share"` and `"keep"` are rejected.
- `history` contains completed rounds as `(my_decision, opponent_decision)` tuples, oldest first. It never includes the opponent's current decision. A separate copy is passed to each strategy.
- The first call uses `round_number == 1` and empty history. Round numbering stays absolute when the history window is limited.
- `resource_multiplier` is the actual tournament setting, not a hardcoded value.
- `import random`, `from random import ...`, and equivalent `math` imports are supported. Other imports, file access, and introspection are rejected. Printing is ignored.
- Globals and random state persist within a match. Each competitor receives a fresh interpreter before **every** match, including winner-stays rematches and independent twins. Advancement preserves tournament eligibility; it does not preserve Python state.
- Both decisions are collected before either history is updated. A call that exceeds three seconds stops the match. Runtime downloading has a separate 60-second limit.

The restrictions are defensive classroom validation, not a security sandbox for hostile code. The browser executes strategy code locally; no strategy source is submitted to a tournament backend.

## Payoffs and scoring

The classroom matrix remains exactly:

| Left decision | Right decision | Left payoff | Right payoff |
|---|---|---:|---:|
| S | S | 3 | 3 |
| S | K | 1 | 5 |
| K | S | 5 | 1 |
| K | K | 2 × multiplier | 2 × multiplier |

**Only mutual Keep changes with the multiplier.** The allowed multiplier range is 0.5–1.5. The setup panel is for the instructor; the launch reveal is a presentation feature, not a password-protected secret.

Round-robin standings use the sum of a strategy's payoffs across its scheduled matches. Match wins add no bonus. Average payoff per match and per strategy-round are also displayed. Faction points are the sum of their strategies' credited payoffs. Ties share the same rank; equally scoring factions draw.

This follows Axelrod's payoff-based ranking method while retaining your Space Dilemma matrix. Axelrod's original matrix was 3/3, 0/5, 5/0, and 1/1; this viewer deliberately uses your classroom values. His first tournament used 200-round matches and five repetitions. Your **Tournament 1** uses the specified 100 rounds and one repetition.

In optional self-play, the two independent seats represent one strategy facing its twin. Their mean payoff is credited **once**, with one match and one set of strategy-rounds. This prevents self-play from awarding a strategy twice the weight of every other opponent. Both seat histories and raw payoffs remain in the rounds export.

Only completed matches enter standings, after playback reaches the end. An incomplete match preserves its completed rounds for inspection/export and awards no standings points. During replay, standings are not credited a second time.

## Tournament formats

| Format | Pairings | Winner |
|---|---|---|
| Tournament 1 | Every F2 strategy versus every F1 strategy; exactly 100 rounds; multiplier 1; full history; one repetition | Highest faction total payoff |
| Custom cross-faction | Every F2 strategy versus every F1 strategy, with configurable rules | Highest faction total payoff |
| Full round robin | Every unique unordered pair across both factions, including same-faction matches; optional independent self-play | Highest faction total payoff |
| Winner stays / elimination | User-selected opening pair; winner stays and faces a selected surviving opponent; loser drops out | Faction with surviving strategies after the other has none |
| Selected matches / no elimination | User-defined ordered cross-faction match queue, optionally repeated | Highest faction total payoff in the chosen queue |

In elimination, one strategy can beat **all** opposing strategies. On a tied match, the viewer pauses for the instructor to choose which strategy advances. The decision is recorded separately and does not change the payoffs. Auto next defaults off when selecting this format so there is time to choose the next opponent; enable it if you prefer the remaining roster order. Elimination is one continuous run and does not repeat its schedule.

Selected queues and elimination can give strategies unequal match counts. Their score rankings are descriptive; elimination is decided by survival, and a manually selected queue measures the selected encounters. Both factions are still required to start with equal roster sizes.

The faction rosters retain their classroom positions in all formats. For a same-faction match in full round robin, both competitors are highlighted in the same roster; the center score labels and colors identify the actual competitors.

## Match length and continuation

Fixed mode plays exactly the selected number of rounds. Probabilistic mode plays at least one round, then continues after each round with probability `p`. The rounds input becomes a **hard cap**, up to 5,000 rounds.

- Uncapped expected rounds: `1 / (1 − p)`.
- Expected rounds with cap `M`: `(1 − p**M) / (1 − p)`.
- At 0%, a match lasts one round. At 100%, every match reaches the cap; uncapped expectation is unlimited.
- At **95%**, the uncapped mean is **20 rounds**; with a 100-round cap, it is approximately **19.88**. This is an expectation, not a guaranteed length.

For historical context, Axelrod's second tournament used 0.00346 termination probability, equivalent to **99.654% continuation**, targeting a median near 200 rounds. It pre-sampled five lengths and reused them across opponents. This viewer's custom continuation mode instead performs an independent seeded continuation trial after each round of each match, as requested; it is not a literal reproduction of that historical scheduling procedure.

## Playback and projection

The center display shows the active competitors' running scores, eight recent completed rows, and a separate current-round stage. Both decisions flash simultaneously; the cells move inward, shrink upward, and join the completed history. Older rows fade at the upper edge. Scores and the trajectory chart update only as rounds are archived.

Use **Pause**, **Step**, **Replay**, **Finish match**, and the speed slider. The speed changes animation timing, not the tournament's decisions. **Auto next** advances after a brief match result pause. Click a completed grid cell or encounter's Replay button to review that match; use Next match to resume an active tournament. Press Space to toggle playback when focus is outside controls. **Project** requests browser full-screen mode.

Setup provides faction labels, four color profiles, and gentle motion. The operating system's reduced-motion preference is respected initially. On small screens, the faction rosters remain left/right above the match viewer.

Each match is computed once, then animated from its recorded decisions. Replay and exports never execute a strategy again. Large tournaments take time: every new match starts two fresh Python workers, and normal playback takes about two seconds per round. Increase playback speed or use Finish match as needed.

## Seeds, export, and replay

The master seed deterministically derives independent seeds for the left strategy, right strategy, and match ending. Each match's seeds depend on its index, repetition, and ordered strategy IDs. Replay JSON and rounds CSV include the settings, source SHA-256 hashes, derived seeds, and rules version. Reproduction requires the same source files, roster order, pairing choices, settings, and pinned runtime version. Changing strategy filenames changes IDs and therefore seeds.

- **Rounds CSV**: every recorded round, decisions, payoffs, running totals, seeds, source hashes, and completion/credit status. A partial current match is included and labeled.
- **Standings CSV**: strategy rankings and faction totals for credited complete matches.
- **Save replay**: settings and records in JSON, including elimination advancement choices. Strategy source is not embedded.
- **Open replay**: verify recorded payoffs and open the saved visualization without downloading Python. Imported replays are read-only; load faction folders to start a fresh live run.

Downloading records is the persistence mechanism. Refreshing the live page clears an unsaved tournament.

## Troubleshooting

**`runner.py` is missing / 404:** this host-owned file must sit beside `index.html`. It compiles the submitted strategy, supplies its history/round/multiplier, and validates its returned decision. Upload the complete site folder, not only the HTML. The viewer now reports this file error separately from runtime downloading.

**Python runtime download failed:** the initial run needs internet access to `cdn.jsdelivr.net` for the pinned Pyodide 0.27.7 runtime. Schools may filter that domain. Try the published HTTPS page on the classroom network before the session. GSAP is included locally in `vendor/` and does not need a CDN connection.

**Code loads in a roster but fails when launched:** file loading is not execution validation. The error names the Python file, line when available, and round. Check the function signature and return values. There is no automatic replacement strategy or substituted decision.

**Roster file missing:** regenerate manifests or use the provided Actions workflow; check filename capitalization. A static web page cannot discover arbitrary directory contents by itself.

**Content-script/EventEmitter console warnings:** messages from browser extensions do not establish that the tournament code failed. Use the explicit error shown in the viewer to identify a strategy or loading problem.

## Developer checks

Node/npm are needed only for automated checks, not publication or normal use:

```bash
npm ci
npm test
npm run test:runtime
npm run test:ui
# Optional: regenerate the separate offline demo preview.
npm run build:preview
npm run test:preview
```

The core tests verify payoffs, schedules, expectation formulas, score accounting, elimination and tie handling, replay validation, and CSV metadata. Runtime tests execute the **unchanged browser worker** in Node workers with the same pinned Pyodide runtime bytes. UI tests use JSDOM with actual Python matches and actual GSAP timelines to check playback and standings behavior; JSDOM does not validate browser layout or school-network CDN access.

Optional WebMCP tools register only when the browser supports `document.modelContext`. They expose read-back and the same visible playback controls. Their registration, valid/invalid inputs, and state updates are checked with a test registry; a native browser WebMCP context is not required for ordinary viewing.
